# REVIEW.md

Defects found in the starter `app/main.py` (helpers and endpoints), what each one looks like from the outside, and how it was fixed. Search for `BUG` or `FIX` in `app/main.py` to find each fix in the code.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `POST /attendance/punch-in` | When `emp_code` doesn't exist in `employees`, the code reads `emp["shift_start"]` on `None`, raising `TypeError` → 500. | POST punch-in with `emp_code: "EMP000999"` returns 500 instead of 404. | Null check after `find_one`: if `emp` is `None`, `HTTPException(404, "employee not found")`. |
| 2 | `compute_late_minutes` | Truncates to whole minutes with `int()` BEFORE the grace check, so `int(10.0166) = 10` and `10 > 10` is false → 0 even though the employee is late. | R2 example: punch-in 09:40:01, shift 09:30 should give 10 but gives 0. | Compare in **seconds** (`seconds > 600`), then floor to whole minutes (`seconds // 60`). |
| 3 | `list_employees` | `skip = page * page_size` skips the whole first page. `count_documents({})` ignores the department filter and there is no sort. | `GET /employees` (defaults `page=1`) returns `[]` although 6 employees exist; `total` is wrong with `?department=`. | `skip = (page - 1) * page_size`, `count_documents(q)`, `.sort("emp_code", 1)`. |
| 4 | `create_employee` | Check-then-insert: two simultaneous requests with the same `emp_code` can both pass `find_one` and both insert. | Two concurrent POST `/employees` with the same code both return 201. | Unique index on `emp_code` at startup; `insert_one` wrapped in `try/except DuplicateKeyError` → 409. |
| 5 | `POST /attendance/punch-in` | Same race as #4 on `(emp_code, date)`, and the unique `(emp_code, date)` index was never created, so the duplicate handler could never fire. | Two concurrent punch-ins for the same employee and day both return 201. | Unique compound index `(emp_code, date)` created at startup; `DuplicateKeyError` → 409. |
| 6 | Responses of punch-in / punch-out / PATCH / `GET /attendance` | Raw documents leak `_id`/`id`, return datetimes as ISO strings (API wants epoch ms), and old records may miss `history`, `half_day`, etc. | `punch_in` comes back as `"2026-07-06T03:58:00"` and an extra `"id"` appears. | One `serialize_record` builds every attendance response: whitelisted fields, defaults for old records, `to_ms()` for instants. |
| 7 | `PunchInIn.status`, `GET /attendance?status=` | `status: str` accepts any string (punch-in must accept only PRESENT / WFH / ON_DUTY). The list filter accepts garbage too. | POST punch-in with `status: "INVALID"` returns 201 instead of 422. | `Literal[...]` types, so Pydantic returns 422. |
| 8 | `compute_work_hours` | Python `round()` is banker's rounding on floats; R4 wants half-up. | `round(0.125, 2)` gives 0.12, R4 expects 0.13. | `Decimal(seconds) / Decimal(3600)` with `ROUND_HALF_UP` (`round_half_up`). |
| 9 | `compute_overtime` | (a) naive/aware datetimes mixed, (b) overnight shifts ignored (shift end is the next day), (c) no R3 threshold (only count when >= 30 minutes). | Shift 22:00-06:00, punch-out 06:40 gives the wrong overtime; punch-out 18:50 on a 18:30 shift gives 20 instead of 0. | Aware IST end built from the attendance date, +1 day when overnight, floor minutes, return 0 below 30. |
| 10 | `list_attendance` | Loads the whole collection into Python, sorts and slices there. | With ~100k records the response takes seconds and uses a lot of memory. | Filter, sort `(date desc, emp_code asc)`, skip and limit all run in MongoDB, backed by indexes. |
| 11 | `GET /health` | Always returned 200. Must be 200 only if MongoDB answers a ping, otherwise 503. | Stop MongoDB, call `/health`: spec expects 503. | `client.admin.command("ping")`; on failure `HTTPException(503)`. |
| 12 | `PyMongo client` / all datetime maths | Default client returns naive datetimes; they get compared with aware ones (`TypeError` → 500) or read as server-local time by `.astimezone()`. | PATCH with only `punch_out` returns 500; results differ between a UTC server and an IST laptop. | `MongoClient(..., tz_aware=True)`; every datetime read from Mongo is aware UTC. |
| 13 | `POST /attendance/punch-in` (time and date) | `datetime.fromtimestamp()` uses server-local time, not IST, so the attendance date and the late minutes are wrong off-IST. Overnight shifts (R1) are not handled. | Punch-in at 21:55 IST on a UTC server lands on the wrong date; 02:00 punch-in on a 22:00-06:00 shift is dated the wrong day with late = 0. | UTC instants truncated to seconds; `attendance_date()` takes the IST date and moves early-morning overnight punches to the previous day; late minutes use the attendance date. |
| 14 | `PATCH /attendance/{emp_code}/{date}` | Crashes (naive vs aware datetime compare), logs fake "changes" for old records with missing fields, stores history punch times as ints instead of BSON dates, and its history is not converted in `GET /attendance`. | PATCH only `status` on an old record: a bogus `half_day: None → False` change appears; PATCH punch_in alone returns 500. | Aware datetimes throughout; missing fields default to 0/False before diffing; history stores BSON dates; serializer converts to ms at the API edge. |
| 15 | `PunchInIn` / `PunchOutIn` / `RegularizeRequest` `punched_at` / `punch_*` | `Optional[int]` is lax: it accepts floats (`1.0`), numeric strings, seconds-looking values. | `punched_at: 1783312500` (seconds) or `"1783312500000"` returns 201. | `Annotated[int, Field(strict=True, ge=1e11, le=4.1e12)]` → 422. |
| 16 | `EmployeeIn` | No validation: bad `emp_code` pattern, bad email, `shift_start: "25:99"`, equal shifts, `joined_on: "2026-02-31"` are all accepted and later crash analytics with a 500. | POST `/employees` with `shift_start: "25:99"` returns 201; the monthly analytics call then fails. | `Field` patterns / lengths, a `joined_on` real-date validator and a `shift_start != shift_end` model validator → 422. |
| 17 | `create_employee` response | `created_at` stored as naive local `datetime.now()` and returned as an ISO string; spec wants epoch ms. | `created_at` is wrong by 5.5 hours on an IST machine and is a string. | Store aware UTC; return `to_ms(created_at)`. |
| 18 | `list_employees`, `list_attendance` (page / page_size) | No bounds: `page=0` gives a negative skip (Mongo error → 500), `page_size=1000` is allowed. | `GET /employees?page=0` returns 500; R10 wants 422. | `Query(1, ge=1)` and `Query(20, ge=1, le=100)`; `date_from`, `date_to` validated as real dates and `date_from > date_to` → 422. |
| 19 | `POST /attendance/punch-out` | Overtime used the punch-in's own calendar date (wrong for an overnight shift punched in after midnight), and the response added an extra `id` field. | Overnight shift 22:00-06:00, punch-in 02:00: overtime is computed against the wrong day; the response contains `id`. | Use the record's `date` for the shift end; return via `serialize_record` (no `id`). |
| 20 | Analytics: `work_hours` null check | `{"$ne": ["$work_hours", None]}` is true for a MISSING field, so records without work_hours are counted in the average. | `avg_work_hours` is wrong when some records lack `work_hours`. | `{"$isNumber": "$work_hours"}`; sums kept as integer hundredths so the average rounds half-up exactly. |
| 21 | `department_summary` | Joins `employees` for every log row (twice when a department filter is given). | Slow on 100k logs. | Group per employee first, join `employees` once per employee, then group per department. |
| 22 | `late_leaderboard` | The rank window sorted on more than one field. Rank must depend only on `total_late_minutes` (ties share a rank: 1, 2, 2, 4), and the limit must be applied after ranking. | Tied employees get different ranks, or ranks that skip wrongly. | `$setWindowFields` sorted on `total_late_minutes` only; `$match rank <= limit` after it; `$sort` with `_id` as the tie-break for output order. |
| 23 | `department_trend` (pipeline) | `$densify` needs a number or date field; the starter's `_id` was a string and the bounds were strings → error. A department with no logs gives `$densify` nothing to start from, and the headcount, rate and moving average are meant to be computed in the database. | `GET /analytics/departments/{dept}/trend?from=...&to=...` returns 500. | Convert the day with `$dateFromString`, seed one empty row with `$unionWith`/`$documents`, `$densify` per day, headcount via `$lookup`, exact half-up rate, `$setWindowFields` for the 7-day average. |
| 24 | `department_trend` (inputs) | `date.fromisoformat()` on bad input raises `ValueError` → 500, and the range limit is off by one (counted by difference, not by rows). | `from=garbage` returns 500; a 93-day range is accepted. | `parse_ymd()` → 422; reject when the inclusive day count is more than 92. |
| 25 | `GET /admin/explain/{endpoint}` | `aggregate(...).explain()` does not exist on a `CommandCursor` (500 on four endpoints), default verbosity is not `executionStats`, simplified pipelines are explained instead of the real ones, and the result contains ObjectId / Timestamp that aren't JSON-safe. | Any explain call other than `attendance_list` returns 500. | Shared pipeline builders; run the `explain` command with `verbosity: executionStats`; convert the output with `bson.json_util`. |

## Looked at and decided NOT a defect

- **`employee_monthly` working-day count.** Counting Mon-Fri from `joined_on` for a mid-month joiner matches R7.
- **`$dayOfWeek` between 2 and 6.** Mongo numbers Sunday as 1, so 2-6 is Monday-Friday.
- **The `punch_out` update filtered on `punch_out: None`.** This is already the correct way to make two simultaneous punch-outs safe, so it stays.
- **Analytics read the stored `late_minutes`, `overtime_minutes`, `half_day` and `work_hours`.** They don't recompute them, which is what the spec requires.
- **`load_dotenv()` before reading the environment.** It doesn't override real environment variables, so deployment settings still win.
